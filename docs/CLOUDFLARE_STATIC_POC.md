# Phase 1.2 — static compatibility and Cloudflare Pages proof of concept

**Status:** local proof of concept complete; no Cloudflare account, Pages project, Worker, DNS record, production domain, AWS resource, or credential was created.

## Static-export decision

**Approved for the current public surface.** `ELION_BUILD_TARGET=static` selects `output: 'export'` only in an isolated temporary copy of the application. The standard `npm run build` still creates the existing Next.js standalone output for Docker and AWS.

The isolated source deliberately removes only `src/app/api/health` before static build. This prevents a Pages-specific requirement from changing the production/container route. The deployable static artifact is written to the gitignored `out/` directory. Build-time metadata routes are explicitly static because they do not depend on a request.

Use these commands:

```powershell
npm run build:static
npm run preview:static
npm run test:static
```

`build:static` uses `NEXT_PUBLIC_SITE_URL` when supplied, otherwise Cloudflare Pages' `CF_PAGES_URL`, otherwise the local test URL `https://static.elion.invalid`. A real preview must use its actual `CF_PAGES_URL` so canonical and sitemap URLs do not point at localhost or an invented domain.

`preview:static` serves exactly `out/` at `http://127.0.0.1:31338` and applies the same intended header policy for local verification. It is not a Cloudflare emulator: final caching, compression, ETags, preview noindex headers and WAF behavior require a hosted preview.

## Health decision

**Choose B: external HTTPS monitoring for the static public delivery target; no Worker now.**

The existing dynamic `GET /api/health` remains the Docker/AWS health contract. A fully static Pages deployment has no application process or dependency graph to probe, so running a Worker solely to return a timestamp would create cost, code, configuration, and a new failure surface without producing a more meaningful signal.

For the static target, `out/api/health.json` preserves the read-only JSON contract (`status`, `service`, `timestamp`) and adds a `delivery: "static"` field so the document is distinguishable from the dynamic origin response; the Pages `_redirects` rule maps `/api/health` to it. Its `Cache-Control` is `no-store`. A future external monitor must probe the public homepage and `/api/health`; this verifies edge delivery and public routing. It must not be described as an origin or database health probe.

Add a Worker only when an anonymous dynamic API genuinely exists. If that occurs, keep it in a dedicated Cloudflare boundary and send its security headers from the Worker response, not only from `_headers`.

## Cloudflare Pages target architecture

```text
GitHub commit / pull request
  → existing GitHub quality workflow
  → Cloudflare Pages build: npm ci && npm run build:static
  → immutable Pages deployment containing out/
  → temporary *.pages.dev URL only

Cloudflare Pages static delivery
  ├─ generated public HTML, metadata, logo, icon and social PNG
  ├─ _headers: public security and cache policy
  └─ _redirects: /api/health → /api/health.json
```

No Worker, database, binding, secret, or Cloudflare-specific application API is in the proof of concept. Cloudflare-specific files are limited to `cloudflare/pages/_headers` and `cloudflare/pages/_redirects`; the build script copies them into the static artifact. Docker, Terraform, TypeScript, Next.js, GitHub Actions and the future OpenAPI/PostgreSQL/S3/OpenTelemetry boundaries remain intact.

Cloudflare documents a static Next.js Pages build as `next build` with `out` as the output directory. The same documentation advises Workers for applications needing full dynamic Next.js support; that is intentionally deferred because this POC does not need it. See [Cloudflare's static Next.js Pages guide](https://developers.cloudflare.com/pages/framework-guides/nextjs/deploy-a-static-nextjs-site/) and [Next.js static export guidance](https://nextjs.org/docs/app/guides/static-exports).

## Security and cache differences from AWS

| Control | Normal Docker/AWS path | Static Pages POC | Staging verification |
| --- | --- | --- | --- |
| CSP, frame protection, MIME protection, referrer and permissions policy | `next.config.ts` response headers | Equivalent rules in `cloudflare/pages/_headers` | `curl -I` every primary route. |
| HSTS | Controlled by `ENABLE_HSTS` after canonical HTTPS approval | Intentionally absent from `*.pages.dev` POC | Enable at the edge only after the approved custom canonical domain is HTTPS-only and rollback implications are accepted. |
| Cache safety | CloudFront policy plus app behavior | Documents revalidate; hashed `/_next/static/*` assets are immutable; static health is `no-store` | Confirm headers and deploy/rollback behavior at Pages. |
| Origin protection | CloudFront/WAF → restricted ALB → private Fargate | No origin server exists; Pages static assets are the public surface | Enable free DDoS/Bot/WAF controls appropriate to the preview, then inspect false positives. |
| WAF / rate limits | AWS WAF policy in Terraform | Cloudflare configuration is account/zone work and is not created here | Review the available free-rule limits and test only non-production traffic. |
| Preview indexing | AWS staging is separately configured | Pages previews normally receive `X-Robots-Tag: noindex`; the POC also sets noindex for `pages.dev` host patterns | Confirm live header before sharing a preview URL. |

The `_headers` file is necessary because Next.js does not execute its `headers()` configuration in an `output: 'export'` artifact. Cloudflare Pages applies `_headers` to static assets; it does not apply them to Pages Functions, which is another reason not to accidentally add a Worker without response-header tests. Cloudflare's [Pages headers documentation](https://developers.cloudflare.com/pages/configuration/headers/) defines these semantics.

## Performance result

The static build produces a **899.4 KiB** client JavaScript surface, within the existing 1 MB budget. The tiny difference from the normal-build measurement is output packaging, not added client behavior. The new `npm run test:static:performance` command measures JavaScript directly from `out/_next/static/chunks`; `npm run test:static` runs the static build, that budget check, and the local route/header/asset smoke test.

Static delivery removes the always-on Node process, ALB hop and container cold/replacement path for ordinary public pages. Cloudflare Pages supplies final CDN caching, compression and ETags at deployment time; measure Core Web Vitals, mobile rendering and regional response time in the hosted staging preview before any public-domain decision.

## Operational differences and failure analysis

| Event | Static Pages behavior / POC control | Remaining staging check |
| --- | --- | --- |
| Build failure | `npm run build:static` fails nonzero and does not produce a new usable artifact. | Confirm Pages retains the prior deployment when its build fails. |
| Bad release | Each Pages deployment is immutable; the operator selects a prior known-good deployment/commit. | Exercise an actual preview rollback and record the deployment ID/SHA. |
| Missing asset | Static smoke test requests logo, favicon, icon and social image; Pages returns the static asset or 404. | Check browser console/network in hosted preview. |
| Static health unavailable | External monitor sees `/` or `/api/health` fail. There is no origin process to restart. | Configure an approved alert recipient and recovery owner. |
| Worker unavailable | Not applicable: no Worker is deployed. | Reassess only if a future dynamic API is introduced. |
| Cache concern | Versioned static assets are immutable; documents revalidate. | Test a Pages deployment update and one rollback. Do not add broad custom zone cache rules. |
| DNS/domain error | POC remains at `*.pages.dev`; production DNS is untouched. | Never attach a canonical domain until human approval. |

## Cost assumptions

The local POC costs `$0`. A Pages staging preview can remain at the provider's free-tier allocation, subject to current terms, fair use, build limits and no SLA. No custom domain is needed for the preview. This is not a commitment that all Cloudflare services or future dynamic APIs will remain free.

## Exact staging-preview procedure (human-operated)

1. Create a dedicated branch or pull request, such as `cloudflare-static-poc`; do not use the final production domain or alter DNS.
2. In a Cloudflare account owned by ELION, create a new, separate Pages project named for the POC (for example `elion-static-poc`). Connect only this repository through the Cloudflare GitHub App.
3. Configure the project with Node `20.19.0`, build command `npm ci && npm run build:static`, and build output directory `out`. Enable build caching only after the first reproducible build.
4. Do not attach any custom domain. Use the project `*.pages.dev` and pull-request hash preview URL only. Pages previews are public by default; restrict them with Access before sharing if the organization requires it.
5. Let `CF_PAGES_URL` provide the build URL. Do not set `NEXT_PUBLIC_SITE_URL` to the future production domain. Confirm the rendered canonical, sitemap and robots output name the temporary deployed URL.
6. Keep production deployments disabled or point the Pages project's production branch to the dedicated POC branch. Configure preview branch controls so ordinary `main` commits do not become the POC's Pages production deployment.
7. Run `curl -I` and browser checks against homepage, every public route, `/api/health`, sitemap, robots, manifest, icon, social image and official logo. Confirm CSP and `X-Robots-Tag: noindex` on preview URLs.
8. Test a deliberately failed preview build, publish a harmless visual change, roll back to the previous immutable Pages deployment, and record the SHA/URL. Do not test against a production domain.
9. Check desktop, tablet, mobile, keyboard/screen-reader flow, real browser performance, cache behavior and WAF false positives. These have not been browser-validated locally because this environment has no maintained browser test runner.
10. Only after written review may ELION decide whether to attach an approved staging hostname. A production hostname, DNS change and public launch remain separate human approvals.

Cloudflare's [build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/), [preview deployment](https://developers.cloudflare.com/pages/configuration/preview-deployments/), [custom-domain](https://developers.cloudflare.com/pages/configuration/custom-domains/), [serving/caching](https://developers.cloudflare.com/pages/configuration/serving-pages/), and [Git integration](https://developers.cloudflare.com/pages/configuration/git-integration/) documentation are the authoritative setup references.
